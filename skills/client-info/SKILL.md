# Skill: client-info

## Назначение

Этот скилл НЕ делает внешний ресёрч сам.
Его задача — собрать для Perplexity качественный prompt на исследование конкретного клиента
с учётом:

1. канонической продуктовой витрины Б&П;
2. классовых маршрутов;
3. отраслевых сборок;
4. ограничений по DLP / client-facing.

На выходе скилл должен отдавать ГОТОВЫЙ PROMPT, который пользователь вставляет в Perplexity.
Perplexity дальше сама делает web research, собирает client-info и предлагает релевантные продукты
из переданного продуктового контекста.

---

## Что считать источником правды

Источник правды по продуктам — продуктовая витрина 02.4:

- индекс продуктов;
- карточки направлений;
- карточки продуктов;
- отраслевые сборки;
- классовые / надпродуктовые маршруты.

Полная сводка витрины — это снимок для чтения, а не первичный источник.
При конфликтах приоритет у канонических карточек и индекса 02.4.

## Что должен сделать скилл

Когда пользователь пишет:

- "подготовь prompt для клиента X"
- "собери prompt для ресёрча клиента X"
- "используй этот скилл для [компания]"

ты должен:

### Шаг 1. Определить задачу

Понять, что именно нужно от Perplexity:

- client-info перед встречей;
- ABM / sales-letter;
- первичный account research;
- проверка рисков;
- подбор релевантных продуктов;
- prep к КП / защите / discovery.

Если цель не указана явно, по умолчанию:
"собрать client-info + product fit + questions for meeting + sales letter outline".

### Шаг 2. Определить клиентский контекст

Собрать из запроса и ближайшего контекста:

- client_name
- отрасль / тип компании
- география
- что уже известно из внутреннего контекста
- какой тип касания планируется: письмо / встреча / КП / ABM
- есть ли гипотезы по ЛПР
- есть ли фокус по продуктам

Если чего-то не хватает — не останавливайся, а заполни как unknown / not provided.

### Шаг 3. Выбрать продуктовый контекст из витрины

Не вставляй в prompt всю витрину целиком.
Собери компактный продуктовый контекст по следующей логике:

#### 3.1. Отраслевой слой

Если у клиента есть явная отрасль, сначала проверь наличие отраслевой сборки.
Используй её как sector preset.

#### 3.2. Классовый маршрут

Если в задаче виден типовой паттерн, проверь классовые маршруты:

- Управляемость прибыли и исполнения
- Управленческий triage / Ремонтная бригада
- Стратегия в портфель инициатив

Если маршрут подходит — добавь его в context как preferred_route.

#### 3.3. Product shortlist

Собери shortlist обычно из 5–12 продуктов.
В shortlist включать:

- только канонические продукты из витрины;
- в первую очередь продукты со статусом "заполнен" или "заполнен (пример)";
- продукты со статусом draft / заглушка / не начат — НЕ включать в auto-pool, если пользователь не попросил явно.

Каждый продукт описывать кратко, в машинно-прикладном виде, а не длинной карточкой.

Формат одного продукта:

```yaml
- id: "3.1"
  name: "Постановка операционной системы работ"
  domain: "управленческий консалтинг"
  status: "filled"
  auto_recommendation: true
  one_liner: "Выстраивание управленческого ритма: совещания, KPI, отчётность, роли, метрики, RASCI."
  client_pains:
    - "много совещаний, мало исполнения"
    - "нет управленческого ритма"
    - "ответственность размыта"
  trigger_patterns:
    - "рост компании"
    - "масштабирование площадок"
    - "хаос управления"
  typical_buyers:
    - "CEO"
    - "COO"
    - "директор по развитию"
```

### Шаг 4. Сформировать правила матчинга для Perplexity

В каждый итоговый prompt обязательно встраивать секцию matching_rules:

```yaml
matching_rules:
  - "сначала определить 5–10 сигналов клиента из открытых источников"
  - "затем свести сигналы к 1–2 типам потребности"
  - "затем матчить на preferred_route и sector_preset"
  - "после этого выбрать не более 3 продуктов из product_shortlist"
  - "не предлагать продукты вне переданного пула"
  - "приоритет у продуктов со статусом filled"
  - "отдельно указать primary_offer и secondary_offer"
  - "отдельно показать почему продукт релевантен именно сейчас"
```

### Шаг 5. Встроить DLP-ограничения

В итоговый prompt всегда добавлять блок safe-use rules:

```yaml
safe_use_rules:
  - "использовать только публичные и проверяемые источники"
  - "данные из судебных споров, ФССП, банкротств и прочих риск-источников помечать как internal_only"
  - "не использовать данные о физлицах как client-facing аргумент без необходимости"
  - "не придумывать продукт вне переданного product_shortlist"
  - "не использовать внутренние CRM-заметки как публичный аргумент"
```

### Шаг 6. Выдать только готовый prompt

Твой финальный ответ — это не объяснение, а готовый prompt для вставки в Perplexity.

## Канонический шаблон prompt-а для Perplexity

Используй этот каркас как финальный output.

```text
Задача: собрать client-info и product-fit по клиенту "{{client_name}}".

Контекст:
- Компания: {{client_name}}
- Отрасль / тип: {{industry_or_type}}
- География: {{geography}}
- Тип задачи: {{research_goal}}
- Что уже известно: {{known_context}}
- Предполагаемый формат касания: {{touchpoint_type}}

Собери:
1. confirmed_facts — только проверяемые публичные факты;
2. external_public_facts — важные сигналы из новостей, сайта, вакансий, публичных источников;
3. pp_inference — аккуратные выводы из открытых сигналов;
4. hypotheses — что нужно проверить на встрече;
5. questions_for_meeting — 5–7 хороших вопросов;
6. key_contacts — публично видимые топ-роли / ЛПР, если находятся;
7. recommended_products — максимум 3 продукта из переданного ниже пула;
8. sales_letter_outline — hook, pain frame, solution teaser, CTA;
9. do_not_use_client_facing — список чувствительных вещей, которые не стоит выносить в коммуникацию.

Product-fit context:

sector_preset:
{{sector_preset_block}}

preferred_route:
{{preferred_route_block}}

product_shortlist:
{{product_shortlist_block}}

matching_rules:
{{matching_rules_block}}

safe_use_rules:
{{safe_use_rules_block}}

Требования:
- Используй публичные источники РФ: ЕГРЮЛ/агрегаторы, сайт компании, вакансии, СМИ, отраслевые медиа, госданные, если уместно.
- Если встречаются чувствительные данные (суды, долги, исполнительные производства), отражай их только как internal_only и не используй как client-facing аргумент.
- Не предлагай продукты вне product_shortlist.
- Сначала определи сигналы клиента, потом выбери primary_offer и secondary_offer.
- Для каждого рекомендованного продукта кратко объясни: почему сейчас, почему этому клиенту, почему этому ЛПР.

Верни ответ в структуре YAML:
client_info_packet:
abm_view:
recommended_products:
sales_letter_outline:
```

## Логика выбора продуктов из витрины

Используй такой приоритет:

1. Сначала отраслевой preset, если он существует.
2. Затем классовый маршрут, если он лучше объясняет тип клиентской проблемы.
3. Затем shortlist продуктов.
4. Затем фильтр по статусу:
   - filled / заполнен → можно включать;
   - заполнен (пример) → можно включать осторожно;
   - draft / заглушка / не начат → не включать в автоподбор.
5. В итоговый product_shortlist выводить только то, что реально нужно Perplexity для выбора.

## Когда спрашивать уточнение у пользователя

Спрашивай уточнение только если без этого prompt будет слишком расплывчатым.
Например:

- не ясно, какую именно компанию имеют в виду;
- неизвестно, речь про prep к встрече или про ABM-касание;
- пользователь хочет очень узкий фокус, а ты не понимаешь какой.

Во всех остальных случаях лучше выдать prompt сразу.
