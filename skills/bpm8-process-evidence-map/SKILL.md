# Доказательная карта процессов, передач и проблем

## Назначение и границы

Результат — единая содержательная модель, из которой пользователь может перейти от верхнего потока к реальной работе, её входу/выходу, разрыву, последствиям и проверяемому свидетельству. Интерактивный HTML — представление модели, не её доказательство.

Это отдельная повторяемая задача с собственным контрактом узлов, передач, влияния и сверки версий. Не расширять ради неё Rail (контроль хода проекта), BPM Exchange (маршрутизация знаний) или pp-slidument (сборка презентаций). Обычный клиентский HTML без процессной модели остаётся у владельца своего результата. Не создавать второй скилл с BPV-префиксом для той же сборки.

Режимы: сборка из сырья; дельта новой фактуры; QA готовой карты; подготовка согласованной модели к передаче. Запрос на анализ не разрешает редактировать файл, запрос на сборку карты не разрешает внешнюю запись или объявление внедрения. Новые файлы создавай только в разрешённом пользователем контуре.

## Подключение норм

Определи фактический класс источников, Old / New Delivery и права записи. Подключи действующие предметные контракты по AGENTS. Скилл не требует организационного Old Delivery для технологической задачи.

Найди корень PP из проекта/конфигурации; не сканируй домашнюю папку. Прочитай применимый раздел стандарта:

`Vault/10-отделы/05-качество-БП/Бизнес-процессы/04-производство/BPV — Внедрение/07-операционная-эффективность-и-себестоимость.md`

Раздел: **«Доказательная процессная модель и интерактивная карта — 15.10.2026»**. Для диагностики прочитай BPM-8 README в `BPM — Майнинг/OPM/EXEC/BPM-8/`. Перед BPV-атрибуцией проверь живой `00-Канонический реестр BPV и суб-BPV.md`, а не старое название файла. Если контракт недоступен, не канонизируй маршрут; независимую инспекцию продолжай с ограничением.

Наследуй сквозной стандарт структурных аналитических артефактов из AGENTS. До сборки назови тип структуры, решение, охват, методологическую опору, физические источники/права, гейт полноты, существующий файл и владельца дальнейшего использования. Для процессного графа используй охват/трассировку/последовательность, а не декоративную MECE-оценку. Для вложенной классификации, заявляющей полноту, отдельно проверь критерий деления и остаток.

## Сборка

1. **Зафиксируй исходник.** Найди проектную карточку, действующий каркас, карту проблем, доказательную матрицу и прошлую интерактивную версию. Сними версию/контрольную сумму входного артефакта. Не считай новую копию того же пути старой версией.
2. **Разреши сырьё.** Составь ограниченный манифест физических интервью, наблюдений и документов исполнения. Для каждого нужны тип, дата/версия, права, статус полноты и локатор. Сводка не подменяет полный транскрипт; полный BPM-2-инжест требует попытки восстановления по его контракту. Один разговор учитывай один раз. Короткий код источника разрешай через его реестр, не по совпавшему номеру.
3. **Извлеки работу.** Из прочитанного фрагмента получи субъект, действие, объект, результат, получателя и контекст. Привяжи операцию к принятому этапу по результату. Не добавляй три операции к каждой ветви для симметрии. Необследованные функции показывай отдельно от отсутствующих и от целевых.
4. **Восстанови передачи.** Укажи отправителя, получателя, объект/версию, условие запуска, запись, владельца передачи и критерий готовности. Не подменяй материальное движение документным. Отдели ветвление, параллельную работу, возврат, условный маршрут, промежуточную приёмку и финальное закрытие. Неустановленные поля оставляй видимыми.
5. **Размести проблемы.** Сначала сформируй нейтральный частный сигнал с субъектом/контекстом и доказательством; потом сопоставь укрупнённой теме. Сохраняй различие симптома, причины, следствия, противоречия и открытого сигнала. Не повышай эпизод до системной частоты. Наличие документа не доказывает его использование.
6. **Покажи влияние.** Место возникновения проблемы, место проявления, другие затронутые операции и причинный механизм — отдельные поля. Для влияния укажи условия, свидетельство, альтернативы и следующий тест. Тематическая связь или перечень смежных рёбер не доказывают причинность. Гипотезы сохраняй как гипотезы.
7. **Сверь историю.** Для старых процессов, операций и проблем покажи «сохранено / разделено / объединено / не размещено», адрес нового объекта и основание. Не смешивай P-коды разных словарей. Новый источник сначала получает дельту «появилось / усилилось / ослабло / противоречит / без изменений / требует проверки»; переписывай всё дерево только при структурном основании.
8. **Свяжи предложения.** Сохрани отдельные поля факта, интерпретации, рекомендации и принятого решения. Материальную процессную проблему свяжи с принятой коммерческой целью по BPM-8 либо покажи запрос. Не выдумывай цель, бюджет, экономию или срок внедрения. Рекомендация не является автоматической задачей.

## Содержательная модель и представление

Храни единый набор устойчивых идентификаторов и связей; таблица Markdown и HTML не должны расходиться из-за двух независимых ручных списков. Точный JSON-формат выбирай под задачу, а не копируй имена полей клиента.

- Работа: код, родитель, субъект, вход, результат, исполнитель/владелец или пробел, версия и источники.
- Передача: откуда → куда, объект/версия, условие/готовность, запись, ответственность, состояние и доказательство.
- Проблема: код/нейтральный текст, работа возникновения, тип, контекст, частота/ограничения, доказательство и следующий тест.
- Влияние: проблема → затронутая работа/результат, механизм, условия, подтверждённость, источник и проверка. Это не тот же тип ребра, что передача.
- Доказательство: физический источник/версия/права, локатор, выдержка либо маркированный пересказ, что подтверждает, предел вывода, статус и уверенность.
- Изменение: проблема → предлагаемое правило/работа → проверенный БПВ → адресат согласования и критерий; решение/исполнение/приёмка/эффект раздельны.

Не своди тип источника, достоверность, состояние процесса и принятие решения к одному статусу. Удобные технические ключи не превращай в английскую управленческую таксономию: подписи и легенда для пользователя — по-русски.

Три уровня доступа: компактный обзор → подпроцессы/операции и передачи → боковая карточка проблемы с доказательством и влиянием. Конкретный лимит обзорных блоков согласуй по запросу; не закрепляй «20» для всех компаний. Если нужен только MD, не навязывай HTML. Если нужна дека, передай содержательную модель в действующий презентационный маршрут, не вводи SI-коды самостоятельно.

Подсветка различает выбранную проблему, работу возникновения и затронутые работы. Легенда объясняет направление, тип связи и неподтверждённость не только цветом. Пользователь может открыть источник и вернуться к выбранному контексту. Поиск и фильтры не скрывают остаток охвата.

Клиентский пакет анонимизирует респондентов по действующим правилам. Не прикладывай сырые интервью, персональные оценки, закрытые ссылки и компьютерные пути автора по умолчанию. Дай разрешённую краткую выдержку/пересказ рядом с утверждением и доступный локатор; точную атрибуцию держи в разрешённом внутреннем реестре. Проверяй работоспособность пакета из его фактической клиентской папки.

## Проверка и передача

До материального изменения используй сценарии [references/evals.md](references/evals.md); после — повтори затронутые проверки. Различай статическую проверку, рассуждательную симуляцию и реальный пользовательский прогон.

Проверь идентификаторы, родителей/циклы вложенности, концы связей, старые→новые адреса, полноту размещения в заявленном охвате, доступность и права доказательств. Отчёт об исключении лучше молчаливой потери узла. Наличие `proof`-поля не подтверждает смысл цитаты: выборочно сверяй материальные утверждения с физическим сырьём, а объём непроверенного указывай.

Для HTML проверь в браузере: обзор → процесс → операция → проблема → влияние → свидетельство → возврат; поиск, фильтр, сценарий ветвления и согласованные размеры экрана. Технический успех не закрывает смысловую проверку. При отсутствии браузера назови ограничение и не заявляй готовность интерфейса.

Основной внедренческий маршрут — BPV-07.6 «Процессно-ролевая модель и должностные инструкции». BPV-07.5 «Непрерывное улучшение бизнес-процессов» получает цикл изменения и повторного замера; BPV-07.7 «Проектное управление и мультипроектная среда» — согласованные проектные правила. Не присваивай BPV-12 по факту сети стрелок: ему нужны расчёт и операционное применение приоритетов/последовательности/мощности.

Для закрытия этапа покажи договорный результат → физический выход/версия → ограничение → требуемое решение клиента, если это входит в запрос. Карта — навигация пакета, не доказательство выполнения всех пунктов договора. Для внедрения отдельно нужны согласованная версия, хранитель, доведение правил и реальное использование; эффект подтверждается своим измерением.

В ответе укажи: что и где изменено; охват/остаток; какие связи подтверждены и какие требуют теста; какие проверки фактически проведены; что передано дальше и что не объявлено внедрённым. Не меняй ClickUp по общей просьбе синхронизации.
