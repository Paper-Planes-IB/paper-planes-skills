# /tunnel

## Назначение

Маршрутизация ценных данных по архитектуре Vault: определить, какие содержательные находки должны попасть в существующие отделы, контуры, артефакты, карты, трекеры, витрину, базу знаний или контентные контейнеры.

`/tunnel` не является `/meditate`: он не ищет ошибки агента и не создаёт правила работы. Также это не обычный `/summary`: он не просто подводит итоги, а предлагает маршрут движения знания через существующую систему.

## Когда использовать

- `/tunnel`
- `туннель`
- `разнеси по отделам`
- `разложи по контурам`
- `куда это в Vault`
- `что полезно для 1/2/4/5/6/8`
- `маршрутизируй знание`

## Не использовать для

- Процессной рефлексии по ошибкам агента.
- Обычной содержательной выжимки без маршрутизации.
- Свободной классификации без проверки реальных контуров Vault.

## Разрешение на создание файлов

Если Илья явно говорит `туннелируй`, `протуннелируй`, `разнеси по отделам`, `разложи по контурам`, `запускай post-archive tunnel`, `ретро не будет, туннелируй` или близкую формулировку, это считается прямым разрешением создавать новые посадочные файлы, когда без них знание не попадает в нужный контур.

## Принцип update-first

При создании единиц знания, методических файлов, процессов, посадок в отделы и других артефактов в рамках `/tunnel` сначала искать существующий смысловой дом и дописывать / обновлять его, если это усиливает уже существующий файл.

Новый файл создавать только если:

- тема действительно новая и не имеет подходящего существующего дома;
- существующий файл станет перегруженным, смешает разные сущности или потеряет управляемость;
- нужен отдельный посадочный файл по правилам контура: отдельная knowledge-unit, отдельный процесс, отдельный training unit, отдельная карточка продукта / МПП / кейса;
- Илья прямо просит отдельный файл или формат.

В tunnel-preview для каждой единицы знания явно выбирать тип действия:

- `update existing` — дописать существующий файл;
- `new file` — создать новый файл, потому что существующего дома нет или он не подходит;
- `no-op` — не писать, но зафиксировать причину;
- `candidate` — оставить как будущую посадку после проверки источников.

Если есть сомнение между `update existing` и `new file`, по умолчанию выбирать `update existing` и кратко объяснять, почему существующий артефакт выдержит добавление.

Минимальный ожидаемый результат такого туннелирования:

- `8-ка`: knowledge-unit / batch knowledge-check / запись в реестр или отдельный посадочный файл Фабрики знаний.
- `5-ка`: методологическая единица, SCQA / архетип / SI / BPV / BPP / линия методологии.
- `1-ка`: training unit, упражнение, рубрика, гейт или ссылка в учебную матрицу; предметный BPV сохраняется, а образовательный продукт зеркалируется в BPV-14 и BPV-14.R.
- `2-ка`: контент-кандидат, кейсовый донор, МПП, витринная или weekly-doc посадка.

### BPV downstream check

Если tunnel-сигнал может стать внедренческим механизмом, не ограничиваться маршрутом `knowledge -> SI -> training/content`. Выполнить BPV-check:

```text
tunnel signal
-> affected BPM / SI / Storyline slide_id
-> approved deck artifact/version and approval decision, or explicit non-deck approved decision
-> possible BPV / sub-BPV / gate / proof metric / skill-only
-> reverse BPV link to BPM / SI / slide / approved decision
-> BPV-sequence impact
-> 5-ка / 1-ка / 2-ка downstream
```

Правила:

- сначала читать канонический реестр и искать существующий родитель в `BPV-01...BPV-14`;
- не создавать новый верхний BPV, если сигнал является sub-BPV, gate, proof metric или skill-only;
- если сигнал затрагивает `МПП`, считать родителем `BPV-03.7 Материалы поддержки продаж`, а `BPV-04.4 Подготовка КП и ТКП` — смежным процессом;
- CRM маршрутизировать в `BPV-05.1`, подготовку данных/архитектуры/автоматизации — в `BPV-05`, аналитику — в `BPV-10`, RAG/ИИ — в `BPV-11`, DPM/sequence — в `BPV-12`, обучение — зеркально в `BPV-14`;
- если сигнал пришёл из Storyline-Storyboard или BPM-SI, показать slide-intent / SI, slide_id, deck/version и событие утверждения; неутверждённый слайд остаётся `BPV candidate`;
- после принятого BPV-route записать обратную ссылку из BPV на source BPM, SI, slide_id и утверждённое решение;
- если появляется training unit, сохранить предметный BPV и добавить соответствующий `BPV-14.x` + `BPV-14.R`, либо явный no-op;
- если BPV-связь проверена и не применима, записать явный `BPV no-op`.

Если отдельный файл не создаётся, агент обязан явно зафиксировать причину no-op в существующем артефакте соответствующего отдела. Простая запись маршрута в паспорте проекта не считается достаточной посадкой в отдел.

## Обязательная логика

Перед выводом или правками проверять существующие опорные файлы соответствующих отделов и ссылаться на них в логике решения. Если опорные файлы неизвестны или могли измениться, сначала искать их в Vault.

Если материал содержит рыночную фактуру, продуктовые гипотезы, клиентские JTBD, категорийные наблюдения, технологические ставки, данные по спросу / каналам / фасовке / ингредиентам или кейсы внедрения продукта, обязательно добавлять отдельный маршрут `отраслевые / продуктовые файлы`. Это не заменяет проектные треки: один и тот же факт может одновременно идти в проектный контур клиента, отраслевой контекст, продуктовую витрину, контент-кандидаты, методологию процессов и учебные кейсы.

## Штабной project-wide preflight

Если текущий чат по `Карта-чатов.md`, реестру чатов, карте коммуникаций или субпаспорту связан с контуром типа `штаб проекта`, `/tunnel` всегда маршрутизирует знание на масштабе всего проекта, а не только текущего физического чата.

Перед маршрутизацией нужно:

- найти `Карта-чатов.md` / реестр чатов ближайшего проектного контура;
- определить штабной чат и связанные чаты / треки / субпаспорта проекта;
- проверить проектные артефакты, где знание уже могло быть частично приземлено: трекер, Storyline / Storyboard, гипотезы, рынок / конкуренты, meeting notes, субпаспорта и journal;
- после этого строить маршруты в 1/2/4/5/6/8 и отраслевые / продуктовые дома от project-wide картины.

В ответе preflight показывать кратко: `штаб проекта -> project-wide tunnel -> какие чаты / треки / проектные артефакты учтены`. Если реестр чатов не найден, явно написать, что проектный штабный scope не подтверждён, и работать по текущему чату / ближайшему проектному контексту.

Базовая карта:

- `1-ка` — обучение: роли, грейды, учебные модули, упражнения, рубрики, гейты, training impact.
- `2-ка` — продажи-маркетинг, продуктовая витрина, МПП, контент-кандидаты, weekly-doc, draft, кейсы и внешняя упаковка.
- `4-ка` — производство, проекты, этапы, CLOSE, ретроспективы, fullkit проекта, внедренческий цикл.
- `5-ка` — качество БП и методология процессов: BPM / BPA / BPO / BPI / BPP, стандарты, readiness, fullkit, внедренческие процессы.
- `6-ка` — новые бизнесы, КОД, внешние продукты, внутренние инструменты, продуктовые гипотезы.
- `8-ка` — Фабрика знаний: reusable-единицы знания, SECI / Nonaka, реестр единиц, knowledge-check, судьба знания.

## Workflow

1. Выделить содержательные единицы, которые имеют ценность для системы.
2. Проверить реальные опорные файлы и контуры Vault по затронутым отделам.
3. Отдельно проверить отраслевые и продуктовые дома, если в материале есть рыночная / продуктовая фактура.
4. Для каждой единицы определить управленческую функцию: что отдел должен получить и какой артефакт может измениться.
5. Отделить прямые правки от кандидатов на будущую фиксацию.
6. Применить `update-first`: для каждой единицы сначала выбрать существующий файл для усиления; новый файл создавать только при явной новой теме, неподходящем доме или прямом запросе.
7. Для BPV-сигнала проверить полный lineage `BPM -> SI -> slide -> approved deck/decision -> BPV` и обратную BPV-ссылку; если презентационный слой неприменим, зафиксировать утверждённое non-deck decision.
8. Если пользователь дал tunnel-разрешение, обновить существующие посадочные файлы в 1/2/5/8, создать недостающие только при необходимости или явно записать no-op причину.
9. Проверить, что каждое заявленное направление имеет физическую посадку: существующий обновлённый файл, новый файл с обоснованием или no-op причина в существующем артефакте.
10. Если появляются задачи на внедрение, предложить запуск `/cordos`.

## Формат ответа

Начинать с короткого BLUF:

```text
Нашёл N единиц знания: X можно разнести сейчас, Y требуют проверки источников, Z лучше оставить кандидатами.
```

Дальше таблица:

| Единица знания | Source BPM / SI / slide | Approved deck / decision | BPV route и обратная ссылка | Контур Vault | Что сделать | Статус |
|---|---|---|---|---|---|---|

## Regression Evals

| Case | Expected | Forbidden |
|---|---|---|
| МПП-сигнал | primary `BPV-03.7`, adjacent `BPV-04.4` | `BPV-04 Продажи` как parent |
| data / analytics / RAG / DPM | respectively BPV-05 / 10 / 11 / 12 | old BPV-11 / 12 / 13 / 14 mapping |
| training unit | subject BPV + BPV-14.x + BPV-14.R or explicit no-op | only 1-ка landing |
| unapproved slide | BPV candidate with trace gap | accepted BPV route |
| approved deck | deck/version/decision + reverse BPV link | one-way Storyline-to-BPV note without backlink |

## Writeback / Approval Gate

Этот skill считается рискованным, потому что может разносить знание по отделам, создавать посадочные файлы, менять существующие артефакты, фиксировать no-op причины и порождать задачи.

Перед durable writeback нужно явно показать Илье: список единиц знания, целевые существующие файлы или новые посадки, тип действия (`candidate`, `update existing`, `new file`, `no-op`, `status/frontmatter`, `task candidate`), источник и последствия. Для `new file` обязательно указать, почему нельзя усилить существующий файл. Создание/правка файлов, изменение статусов, frontmatter, реестров и задач допускаются только после явного акцепта Ильи на этот набор действий.

Если пользователь говорит `туннелируй` или `разнеси`, это разрешает подготовить маршрут и предложить writeback. Автоматически писать можно только когда в той же команде явно разрешено внесение правок и посадка не спорная; при сомнении остановиться на preview/diff и спросить.
