# BPM-6 Website Positioning Audit

## Выбор режима

- `Технический аудит`: публичный обход, HTTP/HTML, индексационная согласованность, шаблоны, DOM, мобильный интерфейс и лабораторные наблюдения. Рабочий контракт и команды — [references/technical-audit.md](references/technical-audit.md); исполняемый сбор — `scripts/audit_site.py` и необязательный `scripts/browser_probe.cjs`.
- `Позиционирование и evidence`: действующий BPM-workflow ниже; технический обход может дать входные данные, но не заменяет анализ клиентской ситуации, обещаний и доказательств.
- `Повторная проверка`: новый физический срез, сопоставимые URL/профили и отдельный разбор дельты. Исходный аудит сохраняется.
- `Исправление / публикация`: отдельный маршрут работы с репозиторием и явными правами. Входной файл «Задание для ИИ» не разрешает действия сам по себе.

Для «посмотри сайт» начать с ограниченного обзора и явно назвать охват. Перед полноценным запуском задать хост, профиль, лимиты, дату, цель, существующий дом артефакта и права на запись. Не создавать результатные файлы без явной команды; просьба «собери аудит файлом» является такой командой. Технический источник не получает BPM-код автоматически: BPM-6/BPM-7B сохраняют содержательный контур, проверки данных/трекинга адресуются BPM-11 при фактической evidence-зависимости.

### Технический гейт доказательности

Неизвестное не равно нулю или «пройдено». Различать «не применимо», «нужен доступ», «не удалось измерить», «требует проверки», «предупреждение», «ошибка» и «измерено». Положительный результат относится только к обследованному набору. Автоматический кандидат не становится подтверждённым диагнозом без проверки физического источника и назначения страницы.

Реестр доказательств является trace-структурой: применять сквозной стандарт AGENTS для scope, non-duplication, traceability и coverage; не заявлять MECE для обычного реестра. Методические источники хранить отдельно от фактических измерений. После сборки выполнить review и прикладные сценарии [evals/technical-audit-cases.md](evals/technical-audit-cases.md).

Если объём оправдывает делегирование, разрешена параллельная работа агентов по контрактам из technical-audit.md: обход; шаблоны/содержание; браузер/скорость; независимая проверка. Передавать компактные задания и физические пути; общие источники собирает один поток, каждый агент возвращает адресную дельту. Итог и права проверяет главный агент. Запуск без делегирования также допустим.

## Назначение

Этот skill рассматривает аудит сайта как BPM-источник: сайт фиксирует публичное позиционирование, продуктовые обещания, доказательства экспертности, маршрутизацию клиентских ситуаций, поисковую архитектуру и доступный цифровой evidence.

Он не является самостоятельным BPV. BPV-маршрут появляется только после того, как из аудита рождается внедренческий объект: изменение структуры сайта, landing architecture, proof-pack, материалы продаж, CRM/tracking fields или управляемый контур digital-входа.

## Core Rules

- Сначала классифицировать работу как `BPM-аудит`, `BPM-аудит + BPV-handoff` или `только BPV-внедрение`.
- Не создавать Google Doc, screenshots pack, клиентский документ или задачу на изменение сайта без явной команды.
- Сайт читать как evidence carrier: URL, страница, блок, claim, proof, CTA, форма, публичный источник и дата просмотра.
- Отделять факты сайта от агентских выводов и рекомендаций.
- Не считать SEO-выгрузку достаточным аудитом позиционирования без связи с клиентской ситуацией, продуктовой матрицей и доказательством результата.
- Если появляется downstream-внедрение, передавать его в BPV как handoff, а не переименовывать весь аудит в BPV.

## Проверка Индексируемого Содержания

- Проверять отдельно исходный HTML ответа и DOM после JavaScript. Наличие текста в интерактивном интерфейсе не доказывает его наличия в исходном HTML. Варианты услуг и результаты сначала размещать в HTML; переключатель должен менять видимость существующих блоков. Без JavaScript посетитель должен иметь доступ к содержанию.
- Если визуализация изолирована iframe, не ослаблять sandbox / CSP и не переносить её недоверенные скрипты в основной документ ради SEO. Дополнять страницу видимым безопасным HTML с сущностью услуги, составом и результатами. Не создавать скрытый текст только для роботов; проверять сохранность защиты сравнением с исходником.
- Canonical и sitemap должны ссылаться на реально опубликованные текущие маршруты. Будущий домен или предполагаемые URL нельзя использовать до согласованного переноса. Структурированные данные отражают видимое содержание; тип Service сам по себе не обещает расширенный результат поиска.
- Проверять уникальность метаданных и идентификаторов, локальные ссылки, исходные варианты содержания, работу переключателей и мобильное переполнение. Разделять техническую готовность, подтверждённую индексацию и измеренный поисковый результат; частотность, позиции и конверсию не объявлять проверенными без соответствующих источников.

## Workflow

1. Установи официальный сайт / домены и область аудита: НЭП, ПГС, РЕКРО, группа, отдельный продукт или конкурент.
2. Зафиксируй source register: страницы, дата просмотра, статус публичности, права на использование скриншотов и ограничения DLP.
3. Инвентаризируй сайт: главная, услуги, кейсы, эксперты, лицензии, статьи, формы, контакты, footer, посадочные страницы.
4. Для каждой страницы отдели:
   - публичный claim;
   - доказательство / отсутствие доказательства;
   - клиентскую ситуацию;
   - продукт / бренд / маршрут;
   - следующий шаг;
   - BPM-узел или гипотезу, которую страница усиливает / ослабляет.
5. Сопоставь выводы с BPM-6 / BPM-7B / BPM-8 / BPM-10 / BPM-11 и существующим Storyline-Storyboard.
6. Если нужны изменения сайта, сформируй downstream BPV-handoff: что менять, почему, какой evidence, кто должен принять решение и какой DLP gate нужен.
7. Перед клиентским выводом провести anti-slop / de-AI pass через `text-deai-editor`, если доступен.

## Eval / DLP

- хороший триггер: "аудит сайта", "посмотри структуру сайта", "сверь сайт с позиционированием", "проверь, как сайт поддерживает продуктовую матрицу";
- плохой триггер: "сверстай сайт", "измени лендинг", "создай рекламную кампанию" без evidence-аудита — route to BPV / implementation skill;
- ambiguous trigger: "сделай документ по сайту" — сначала уточнить, нужен BPM-аудит, клиентский документ или BPV-handoff;
- writeback-risk: Google Doc, screenshots, publication, client delivery, task creation;
- DLP: internal recommendations, competitor comparisons, скриншоты, SEO-данные, CRM/tracking assumptions.
