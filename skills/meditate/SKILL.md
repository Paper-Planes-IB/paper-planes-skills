# meditate

## Назначение

Рефлексия по качеству работы агента и рост картотеки правил.

`/meditate` не является содержательной выжимкой чата. Его задача — найти, что в работе агента не получилось сделать сразу, где потребовались лишние итерации, где возникла неверная интерпретация, перерасход токенов, ручная компенсация со стороны Ильи или повторяемый сбой процесса.

## Когда использовать

- `/meditate`
- `медитация`
- `рефлексия`
- завершение нетривиальной сессии

## Не использовать для

- Подведения содержательных итогов чата.
- Конспекта проекта, клиента или обсуждения.
- Переноса интересных находок в отделы Vault.
- Разнесения материала по 1/2/4/5/6/8 отделам.

Для содержательной выжимки использовать отдельный режим `/summary`. Для маршрутизации знания по архитектуре Vault использовать отдельный режим `/tunnel`.

## Источники

- `ПКМ/картотека-правил.yaml`
- `ПКМ/картотека-лог.md`
- `ПКМ/hot.md`
- `Codex/rules/*.md`

## Штабной project-wide preflight

Если текущий чат по `Карта-чатов.md`, реестру чатов, карте коммуникаций или субпаспорту связан с контуром типа `штаб проекта`, `/meditate` анализирует качество работы агента по всему проекту, а не только внутри текущего физического чата.

Перед рефлексией нужно:

- найти `Карта-чатов.md` / реестр чатов ближайшего проектного контура;
- определить штабной чат и связанные чаты / треки / субпаспорта проекта;
- учитывать процессные сбои, лишние итерации, неправильные режимы, неверные writeback / source-check / routing решения по всем связанным проектным чатам и артефактам;
- не превращать это в содержательную выжимку проекта: масштаб project-wide, режим всё равно process reflection.

В ответе preflight показывать кратко: `штаб проекта -> project-wide meditate -> какие чаты / треки / артефакты входят в проверку`. Если реестр чатов не найден, явно написать, что проектный штабный scope не подтверждён, и работать по текущему чату / ближайшему проектному контексту.

## Workflow

1. Найти только процессные сбои: что не получилось с первого раза, где потребовались уточнения, переделки, лишние чтения, лишние файлы, неверный режим или ручная компенсация Ильи.
2. Отделить одноразовый инцидент от повторяемого паттерна.
3. Для каждого кандидата дать формулу: факт → ущерб → причина → контрмера.
4. Проверить, нужен ли результат как правило, anti-pattern, автоматизация, хук, скилл, субагент или инженерная экономия.
5. Сформулировать кандидаты в картотеку кратко и проверяемо, с триггером и анти-триггером.
6. Не править `ПКМ/картотека-правил.yaml`, `.Codex/rules/` и graduated-rulebook без отдельного акцепта Ильи.
7. Если новых правил нет, явно написать: `meditate: новых правил нет`.
8. При завершении сессии предложить обновление `ПКМ/hot.md`, если есть невыводимый из файлов контекст.

## Writeback / Approval Gate

Этот skill считается рискованным, потому что из процессной рефлексии могут родиться новые правила, anti-patterns, hooks, automations, skill patches или изменения в `hot.md`.

`/meditate` по умолчанию только предлагает кандидаты. Записывать правила, менять `.Codex/rules/`, `AGENTS.md`, skills, hooks, automations, `ПКМ/hot.md` или картотеки можно только после отдельного акцепта Ильи на конкретную правку. Фразы про обсуждение сбоя не считать разрешением на запись, пока Илья явно не говорит `запиши`, `исправь`, `обнови правило`, `вноси`.
