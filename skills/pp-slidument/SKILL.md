# PP Slidument Skill

## Коммерческая рамка — решение Ильи 07.10.2026

Для КП действует раздел «Комплексное внедрение; пилоты не предлагаем» в [commercial-proposal-generator](../commercial-proposal-generator/SKILL.md). Предлагать комплексное внедрение в согласованном объёме; проверки и прототипы — внутренние этапы проекта. При сборке и QA исключать пилотный вход из текста, схем, пакетов, стоимости и следующего шага; сохранять прямо заданные границы услуг.


Paper Planes consulting sliduments — dense analytical documents that are read without a speaker, in the style of McKinsey/BCG strategy decks.

## 0. КРИТИЧЕСКИЕ ПРАВИЛА (читать первым)

### PP visual likeness gate

Технически корректный HTML не считается PP-слайдументом автоматически. До PPTX каждый слайд должен пройти визуальное сравнение с `references/pp_pptx_builder_rule.md` и доступным одобренным PP-референтом.

Обязательные признаки:

- канонический фон `#FFFFFF`, основной текст `#181D27` и главный акцент `#FF5850` по `references/visual-style-guide.md`; прежний PAPER/Elevel-фон `#EFEBE7` больше не является каноном;
- реальный логотип Paper Planes как глобальный asset в едином слоте; текст `PAPER PLANES` не заменяет логотип;
- PT Sans как надёжный default для кириллического editable-маршрута, если референт не задаёт другую доступную гарнитуру;
- Проверять гарнитуру после PDF-экспорта по всем текстовым ресурсам, включая отдельные символы. При сборке Paper Planes — международное развитие 07.10.2026 символ `→` вызвал подстановку другой гарнитуры в блоках с PT Sans; замена на обычный текст восстановила PT Sans во всём PDF. Если стрелка нужна для схемы, использовать нативную графическую фигуру и повторно проверить экспорт, а не считать шрифт подтверждённым по основному тексту;
- action title передаёт конкретный вывод;
- слайд заполнен доказательством, механизмом, таблицей, сравнением, схемой решения или другим функциональным exhibit;
- три короткие карточки, крупные пустоты, повторяющиеся card grids и декоративные chips не считаются достаточной аналитической плотностью;
- в деке чередуются согласованные силуэты: таблица, матрица, flow, decision tree, option profile, org view, evidence map, chart, mechanism;
- видимый текст клиентского deliverable проходит `text-deai-editor` в клиентском режиме до статуса `HTML_ready_for_PPTX`; `balakhnin-voice` применяется только по явному запросу на авторскую стилизацию и не является обязательным редактором КП;
- англицизмы, внутренние коды, production terms и паттерны `не X, а Y` удалены либо имеют доказанную предметную необходимость;
- источники и caveats видны рядом с материальными цифрами и утверждениями.

Обязательный статус: `PP_visual_likeness_passed`. `overflow 0/N` подтверждает только отсутствие технического переполнения и не заменяет этот gate.

### Запрет имитации исправления

- Текст правится в исходных данных слайда. Runtime-словари замен, CSS `content`, скрытые дубли и пострендерная подмена не засчитываются как `text-deAI` или `Balakhnin voice`.
- Смена фона, цветов, рамок и accent bars без изменения повторяющегося card-grid renderer считается `skin repair`, а не новой PP-композицией.
- Для visual pass перечислить slide IDs, где реально изменены силуэт и exhibit logic.
- Логотип должен иметь подтверждённый asset path/source; самостоятельно нарисованный похожий SVG не засчитывается как официальный logo asset.
- Гарнитура должна быть загружена/встроена или подтверждена через computed/rendered font, а не только объявлена в CSS.
- До `PP_visual_likeness_passed` обязательны отчёты `pp-text-critic`, `pp-slide-critic` и montage review.

### PP Pages: оболочка отдельно от слайда

HTML-прототип проверяется в двух слоях:

- `slide grammar`: самостоятельные 16:9-слайды, ССА, action title, exhibit, источники, логотип и функциональная кодировка;
- `PP Pages shell`: интерфейс просмотра, который не является частью PPTX.

Обязательный shell: фиксированный/липкий контекст деки; сворачиваемая панель `Слайды`; полный упорядоченный список миниатюр; активное состояние; переход по клику и клавиатуре; фокусный просмотр одного слайда; адаптивность без горизонтального переполнения. Длинная страница из последовательных слайдов без такой навигации не считается PP Pages-прототипом.

Референт оболочки: `https://pages.72-56-234-191.sslip.io/xnv72U7y8WAo/` (предоставлен Ильёй 12.07.2026). Использовать его для shell, плотности и композиционной логики; не копировать клиентские данные. Наблюдаемые цвета не становятся универсальной палитрой автоматически.

Каждый дополнительный цвет должен иметь стабильную функцию: роль, контур, сценарий, статус evidence, риск или состояние решения. Декоративная разноцветность и смена значения одного цвета между слайдами запрещены.

### Markdown-first production source

До HTML/PPTX должен существовать один авторитетный большой Markdown deck-spec. Он является источником видимого текста, логики, доказательств и конструкции; HTML, PP Pages и PPTX только материализуют его. Любая содержательная правка сначала вносится в MD.

### Optional derivative subskill: proposal-template reconstruction

Если входом является уже существующий HTML/PDF/PNG proposal artifact, где нужно восстановить редактируемый текст, разметить `data-block` / `data-field`, сохранить визуальную систему донора или починить proposal template перед дальнейшей PP-сборкой, можно вызвать derivative subskill `html-proposal-template-editor` из `~/.codex/derivative-subskills/html-proposal-template-editor/`.

Этот вызов не делает архив частью skill-корпуса и не отменяет правила `pp-slidument`: production Markdown, claim ledger, PP Presentation Kit, visual likeness gate, critics, contact sheet и client-facing DLP остаются обязательными. Субскилл Давыдова отвечает только за template reconstruction / inspection / validation слой.

Не вызывать его для обычного создания нового PP-слайдумента из production MD, если нет старого HTML/PDF/PNG-шаблона, baked text или задачи editable-template repair.

Стартовый контракт обязателен: использовать `references/deck-content-template.md`, типы из `references/slide_types.md`, палитру из `references/visual-style-guide.md`, процесс принятого пакета `references/kit-2026-07-21-README.md` и правила экспорта из `references/kit-2026-07-12-pptx-builder-rule.md`. Для редактируемого PowerPoint дополнительно читать `references/native-pptx-production-guide.md`. Установлен PP Presentation Kit с обновлением 21.07.2026; более поздние локальные правила этого скилла сохраняют приоритет. Файлы `kit-2026-07-21-*` — снимки оригиналов: внутренние относительные ссылки в них относятся к структуре исходного ZIP; рабочие локальные адреса перечислены здесь.

### Редактируемый PowerPoint — пакет Натальи от 21.07.2026

Прямое решение Ильи от 26.09.2026 — использовать пакет и зарегистрировать его. Исходный ZIP сохранён в `CLAUDE/skill-bundles/PP_presentation_kit_2026-07-21_native_pptx.zip`, SHA256 `9e2b66488558b2929668f4a177a0f5ddbc499cbcfdd30cfa042a08fa6f7076ea`. Корень архива и версия в README остались `2026-07-12`; релиз `2026-07-21` установлен по CHANGELOG и наличию production-гайда. Архив не содержит готового универсального native-PPTX builder: приведённые имена функций — контракт реализации, а не существующий API.

Выбирать режим, если пользователь просит редактируемый PPTX, команда будет менять PowerPoint после встречи или слайды нужны для объединения с другой декой. Содержание и доказательства остаются в существующем производственном Markdown. Последовательность: содержательная проверка → спецификация слайдов → сборка нативных объектов через общий слой функций → рендер и визуальная проверка → текстовый критик → слайдовый критик → исправления и повторная проверка → передача. HTML можно делать как дополнительный просмотр; для явно выбранного нативного режима он не является обязательным промежуточным форматом. Гейты доказательности и визуального соответствия PP применяются к реальному рендеру PPTX.

Технический контракт: 16:9; редактируемые текст, таблицы и схемы; общий слой заголовков, подвалов, источников, логотипа, таблиц, матриц, временных шкал и графиков. Нужны функции проверки вписывания текста, очистки повторно используемого слайда и удаления теней. Имена из гайда допустимо адаптировать к используемой библиотеке. Основной текст — от 12 pt, абсолютный минимум — 10 pt; текущий default PT Sans для кириллицы сохраняется, Inter/Arial из пакета выбираются при доступности и соответствии референту. Палитра — существующий `references/visual-style-guide.md`. Логотип — проверенный asset, не текстовая имитация.

Растровый PPTX из полноэкранных PNG не проходит требование редактируемости. Проверить нативные объекты, переполнение и наложения, шрифты, источники, лого/подвалы, отсутствие теней, полный контактный лист и фактическое открытие файла в PowerPoint без предупреждений. Если проверка в PowerPoint недоступна, так и записать; открытие ZIP или проверка XML её не заменяют. Обязательные критики: `agents/pp-text-critic.md` и `agents/pp-slide-critic.md`; их более поздние локальные версии не откатывать на архивные.

Правило обновления пакета: сравнить файлы и даты; сохранить более поздние локальные гейты, источники и авторские инкременты; переносить доказанную дельту, а не заменять весь скилл старым ZIP. Передача архива не разрешает автоматически публиковать материалы клиента, запускать вложенные скрипты или объявлять готовой презентацию. Копию для команды обновлять только по изменённым путям и отражать в существующем манифесте синхронизации.

Проверочные сценарии интеграции: запрос «редактируемый PPTX» выбирает нативный режим; просьба только о плане слайдов не запускает рендер; полноэкранные PNG не проходят проверку редактируемости; более поздние локальные критики и инструкции остаются на месте; размер шрифта менее 10 pt не проходит; отсутствие проверки в PowerPoint не выдаётся за её успешное выполнение. На этапе регистрации проверяется наличие этих контрактов и файлов, а не готовность ещё не созданной деки.

Канонический upstream кита: `https://github.com/ntokaeva/paper-planes-presentation-kit`, ветка `main`. Receipt должен фиксировать upstream commit и drift относительно установленного snapshot; проверенный 12.07.2026 HEAD — `c9aa8b46f1a306f9037d36957bb778ebe990a2cc`.

Для каждого слайда обязательны пять независимых адресов:

1. `sostac_roles` — одна или несколько ролей информации: Situation analysis / Objectives / Strategy / Tactics / Action plan / Control; при смешении отметить dominant role;
2. `structural_class` — technical / normative / reference / consulting / encyclopedic;
3. `slide_intent_id` — какой SI реализуется;
4. `GS_reference / library_address / donor slide` — откуда берётся нормативная конструкция;
5. `visual_pattern` — таблица, decomposition, driver tree, heatmap, waterfall, process, matrix, from-to, roadmap, RASCI или другой exhibit.

`consulting` допустим, когда Question нельзя доказать нормативным GS; обязательны `normative_proof_status=insufficient`, причина и senior review. SI не является прямым генератором consulting slide. Если уникальный слайд успешно защищён и стал повторяемым, он проходит review, входит в GS как normative и получает новый SI. Для normative/reference слайда отсутствие библиотечного адреса является ошибкой. Неизвестный leaf visual type можно оставить `classification_pending_owner_ingest`, но пять structural classes и шесть SOSTAC roles уже каноничны.

### Машинные ворота перед клиентом

- тип и visual pattern каждого слайда обосновываются в production MD до HTML;
- один силуэт нельзя повторять более чем на двух последовательных содержательных слайдах без принятой причины;
- `интервью и документы`, `материалы проекта` и сходные общие source labels запрещены: нужен named source + доступный locator;
- первые пять слайдов проходят deck-level SCQA;
- обязательны полный contact sheet, overflow/overlap audit и empty-space geometry audit;
- empty-space audit включает semantic-fill check: крупная область с одной общей фразой, существительным-ярлыком или пустой ячейкой считается недозаполненной, даже если геометрия формально аккуратна;
- HTML screenshot, print/PDF и PPTX сохраняют строгий 16:9;
- Для фото в PDF запрещено полагаться на CSS `filter`, `mix-blend-mode` или viewer-dependent цветовые эффекты: разные PDF-просмотрщики могут давать паразитный оттенок. Использовать исходный цвет с нейтральным overlay либо заранее подготовленный растровый asset; после экспорта отдельно проверить страницу в PDF-renderer, а не только в браузере. Если оттенок сохраняется в целевом просмотрщике, сплющить всю проблемную страницу в единый RGB-растр и собрать её как `/DeviceRGB` без ICC-профиля, прозрачности, `/SMask` и `ExtGState`; одной визуальной проверки в Chrome недостаточно.
- каждому основному visual pattern нужен golden HTML/GS/donor reference либо custom-consulting rationale;
- публикация невозможна без отчётов обоих PP-критиков и повторного рендера после исправлений.
- инструментальность результата — предпочтение Ильи 09.10.2026: подпись называет инструмент, его пользователя и рабочее применение. Общие «документы» / «концепции» не заменяют действия команды. Сохранять точные форматы и статус готовности; план не выдавать за работающий инструмент. После замены заголовка проверять соседние ячейки результата и claim ledger. Общий принцип — в AGENTS и стилевом каноне text-deai-editor. Не называть документы итогом: итог — решение или инструмент и применение; обязательные форматы клиента показывать отдельно. Проверять тот же класс ошибки в этапах, итоговом составе, стоимости и следующем шаге.
- язык БПМ / БПВ проходит сквозную проверку по действующим каталогу BPM и реестру BPV: метод, собираемые данные, аналитический результат и проект внедрения различаются; принятые названия сохраняются в production MD, claim ledger, подписи exhibit, кейсах, Гантте и программе. Клиентский перевод хранится в словаре с кодом и границами, а не подменяет процесс произвольным синонимом. Проверочные примеры: анализ конкурентов вместо «досье игроков», продукт и УТП вместо «продукт и аргументы», паспорт проекта внедрения вместо произвольной карточки. Связь источника с результатом нужна фактическая: история заказов не становится сведениями о конкуренте. Внутренние коды не выводятся ради декора и не расширяют scope; после правки обязательны свежие receipts. Решение Ильи 09.10.2026; методический владелец словаря — commercial-proposal-generator.
- задачи физического брифа проходят через всю деку: номера и предмет → работы / методы → этап → инструмент → кейс → Гантт → приёмка и цена. Обзор этапов показывает номера, названия задач и результаты, включая задачи, пересекающие несколько этапов. Проверка выполняется по таблице в существующем production source, а не по числу подписей «1–6». Тематические разделы и критерии приёмки не перенумеровывают задачи клиента; методы и дополнительные инструменты PP не выдаются за новые требования заказчика. Методический владелец — commercial-proposal-generator; прямое решение Ильи 09.10.2026.
- после автоматической замены отдельно проверять исполнение аннотации в распарсенных блоках production source: ожидаемые слайды изменены, принятые фразы присутствуют, запрещённые сняты; при изменении видимой копии её контрольная сумма должна измениться. Нулевое число замен не считать успехом. Совпадение PDF с исходником не доказывает, что сам исходник исправлен. Только после этих проверок выполнять рендер и получать свежие квитанции.
- после пользовательской аннотации старая QA-квитанция недействительна: исправление сначала вносится в production MD, затем выполняются терминологический sweep, повторный рендер затронутых страниц, просмотр полного contact sheet и проверка финального PDF в целевом просмотрщике;

### Сквозная трассировка вложенных скиллов

`pp-slidument` — владелец финальной сборки и сквозной трассы. В этой системе запуск подскилла означает: открыть его актуальный `SKILL.md`, выполнить применимый workflow внутри текущего родительского запуска и принять его квитанцию; это не требует отдельного агента или чата. Упоминание скилла в маршруте не доказывает его запуск. Для каждого клиентского deck-run фиксируй в существующем production MD / QA receipt компактную `subskill_run_trace`; отдельный файл журнала не создавай. Создавай `parent_run_id` как `deck_key@source_revision#annotation_batch` и передавай неизменным всем дочерним скиллам; версию источника фиксируй путём/именем и номером ревизии либо контрольной суммой, если она доступна. Новый пакет пользовательских правок получает новый `parent_run_id`; прежние квитанции по затронутым объектам помечай устаревшими.

Минимальная строка трассы: `parent_run_id | parent_skill | child_skill | child_skill_resource | child_skill_version | trigger_and_scope | input_artifact/version | required_output | returned_output_or_verdict_or_locator | status | next_consumer`. Статусы: `пройден`, `есть замечания`, `пропущен-вне-триггера` с причиной, `заблокирован` с зависимостью, `нужен-повтор`. Для каждого изменения пользовательской аннотации добавь её ID/локатор и укажи, какая предыдущая квитанция стала недействительной.

Обязательные ветви:

- `mece-prezy` — когда строится или перестраивается storyline, структура аргумента или порядок слайдов; для точечной редакторской правки допустимо `пропущен-вне-триггера` с причиной. Его выход — утверждённая storyline/slide-intent, переданная в production MD.
- `consulting-slides-creator` — только для выбора конструкции слайда; всегда передаёт производство в `pp-slidument` и не подменяет его экспорт и QA.
- `text-deai-editor` в клиентском режиме — для всего видимого текста до критиков; возвращает изменения формулировок и незакрытые языковые вопросы, не меняя без поручения смысл, evidence, область правки или верстку.
- `pp-text-critic` и `pp-slide-critic` — запускаются на одной и той же актуальной версии источника/рендера; оба возвращают вердикт, находки с локаторами и версию входа.
- `presentation-qa` — запускается после исправлений и повторного рендера; получает обе квитанции критиков, storyline/claim trace, список аннотаций и регрессионное сравнение.
- `pdf` — если выпускается PDF или правится PDF-only источник; фиксирует рендер целевого PDF-просмотрщика, текстовое извлечение и сверку числа/геометрии страниц. Видимая белая маска поверх старого текста не считается исправлением: если невозможно удалить или заменить старый текстовый слой, статус клиентского PDF — `blocked`.
- `case-narrative` не вызывается для обычного клиентского слайдумента: его scope — кейсы в книге/главе/методическом нарративе. Если такой кейс действительно создаётся в соответствующем жанре, фиксируй запуск отдельно и не выдавай его за универсальный slide critic.

Порядок завершения одного parent run: актуальный production MD → `text-deai-editor` → `pp-text-critic` → материализация и рендер → `pp-slide-critic` → экспорт финального PDF и проверка скиллом `pdf` → `presentation-qa` по уже экспортированной версии → выпуск. Замечания любого этапа возвращаются в production MD; все зависимые квитанции после правки переоткрываются. Не ставь итоговый QA раньше PDF-экспорта и не выпускай версию, отличную от проверенной.

Передачу считай завершённой только если выход дочернего скилла реально существует, относится к текущей версии и потреблён следующим этапом либо явно возвращён на доработку. Самоотчёт `запущен` без артефакта/вердикта не засчитывается. При пропуске обязательной ветви итог — `PP_production_QA_incomplete` или `hold_before_client`.

### Калибровка типических презентаций по правкам Ильи

Если Илья просит запоминать правки как правила, используй замечания как материал для улучшения существующих навыков, а не как разрешение механически универсализировать каждую замену. Сначала исправь авторитетный production MD и всю текущую деку по уже заданному циклу проверки аннотаций. Затем раздели замечание: клиентский факт/решение, частная редактура или переносимый принцип с явной областью применения.

Клиентские числа, имена, выбранные точки, бюджеты и утверждённые решения остаются в проекте. Переносимый принцип дописывай к ближайшему существующему правилу владельца: логика аргумента — `mece-prezy`; композиция, производство и экспорт — `pp-slidument`; язык — `text-deai-editor`; критерий аудита — `presentation-qa`. Не создавай дублирующий навык или параллельный канон. Указывай условие применимости, что именно меняется в действии агента и какую ошибку правило предотвращает; если правило уже есть, проверь исполнение вместо добавления дубля.

Для презентаций о росте сети допустима согласованная владельцем последовательность: численный разрыв до цели и графики факторов, ограничения достижимости, вклад отдельных точек, кандидаты роста, экономические и операционные условия, измеренный вклад инициатив и непокрытый остаток. Это условный отраслевой шаблон, а не обязательное начало любой презентации. Не превращай версию цели в утверждённый план, гипотезу рычага — в доказанный эффект, а приоритет одного города — в запрет остальных.

После переноса правила кратко сообщи Илье, какой существующий навык изменён и где правило применимо. Проверка текста навыка и повторная сборка текущего примера не заменяют независимую проверку поведения на новых задачах.

### Производственный контракт Натальи Токаевой

- Тип визуала выбирается по управленческой мысли, а не по удобству универсального шаблона: причинность показывается причинной конструкцией, сравнение — сопоставимой матрицей, маршрут — этапами и воротами, организация — ролями и интерфейсами, решение — деревом или таблицей условий, доказательство — графиком, таблицей, картой или деревом проблем.
- Один карточный конструктор для разных типов мысли запрещён. Пять связанных шагов собираются в одну причинную схему, а не в пять одинаковых карточек со стрелками.
- До HTML ведётся claim-level evidence ledger: `Claim ID | Slide ID | Exact claim | Source object | Locator | Evidence right | Caveat | Client wording status`. Методический слайд об источниках не заменяет этот реестр.
- Исходный текст production MD должен быть клиентским до рендера. JavaScript/CSS-замены слов и пострендерная русификация не засчитываются.
- Каждый дополнительный цвет имеет словарь `token -> meaning -> allowed objects -> forbidden use`; декоративная радуга запрещена.
- Нарушение любого пункта даёт `hold_before_client`, даже если размер, шрифт, логотип и overflow формально корректны.

### Что такое слайдумент

Слайдумент ≠ презентация для выступления. Слайдумент = плотный аналитический документ в формате слайдов, который читается самостоятельно, без спикера. Аналог: McKinsey blue book, BCG strategy deck.

### ОБЯЗАТЕЛЬНО

1. **Функциональная плотность**: каждый крупный регион слайда выполняет работу — доказывает claim, раскрывает механизм, сравнивает варианты, показывает процесс, решение, владельца, критерий или evidence gap. Фиксированной нормы символов нет; длинный текст без функции и большой пустой блок с одной общей фразой одинаково не проходят gate
2. **Визуализация**: каждый контентный слайд ОБЯЗАН содержать минимум один визуальный элемент — таблицу, график (SVG), карточки, диаграмму, матрицу, или bento-grid блоки. Текст без визуализации = ошибка. Если есть числовые данные — СТРОЙ ГРАФИК, а не пиши числа текстом. См. таблицу «Обязательные визуальные элементы» ниже
3. **Action titles**: заголовок = доказательный вывод, НЕ тема. Число допустимо только при точном источнике и locator. «Три узла передачи проекта не имеют владельца» — да, если узлы подтверждены. «Анализ процессов» — нет
4. **Мало слайдов, много контента**: типичная презентация на 50 страниц PDF = 15-20 слайдументов. НЕ 50 слайдов по 3 буллета
5. **Направление чтения: СЛЕВА НАПРАВО.** Контент на каждом слайде организован горизонтально — колонки, карточки в ряд, таблицы. НИКОГДА не строить слайд сверху вниз (вертикальный буллет-лист). Единственное исключение — строки внутри таблицы
6. **Полная ССА-логика**: каждый содержательный слайд показывает `Situation -> Complication -> Answer`. Факты без объяснения их значения для целей клиента считаются незавершённым слайдом. Заголовок формулирует `Answer`.
7. **Сохранение scope**: все принятые цели deliverable должны иметь видимый маршрут в деке. Нельзя сжимать проект до одной governing question, если это теряет параллельную задачу, например повышение эффективности текущей модели.

### ЗАПРЕЩЕНО

| Анти-паттерн | Почему плохо | Как правильно |
|-------------|-------------|---------------|
| 30+ слайдов с 3 буллетами | Это PowerPoint-караоке, не аналитика | 12-20 плотных слайдументов |
| Текст без визуализации | Нечитаемо, не видно структуры | Таблица, карточки, или график на каждом слайде |
| Заголовок-тема («Конкуренты») | Не несёт информации | Action title: «Три конкурента контролируют 68% рынка» |
| Один буллет-лист на весь слайд | Пустой слайд | 2-3 колонки SCQA + таблица/карточки |
| Вертикальная раскладка (сверху вниз) | Не консалтинговый формат, теряется SCQA | Всегда слева направо: колонки, карточки в ряд |
| Слайды-«спасибо» и «вопросы?» | Пустая трата места | Заменить на Executive Summary или финальные рекомендации |
| Декоративные элементы | Отвлекают от данных | Только функциональная графика |
| Раздувание блока до полной деки | Один тип данных → 1-5 слайдов, не 20 | Определи режим: блок vs полная презентация |
| Числа в тексте без графика | Данные не считываются визуально | Любые числовые данные → SVG-график или диаграмма |
| Три карточки с фактами без вывода | Показана только Situation | Добавить Complication для цели клиента, Answer и exhibit, раскрывающий переход |
| Большая вводная карточка с одной общей фразой | Площадь есть, содержания нет | Показать диагностические вопросы, известное состояние, решение и ожидаемый результат |
| Неподтверждённая цифра или стрелка `X -> Y` | Визуальная уверенность маскирует отсутствие evidence | Указать source+locator или заменить на конкретный качественный механизм |
| Ярлык `Дизайн`, `Запуск`, `Контур`, `Система` | Неясен объект работы | Назвать объект, состав и функцию: `Дизайн структуры`, `Запуск управленческих циклов`, `Операционная система работы компании` |

### Структура типичной презентации

```
1. Титульный слайд (G1)
2. Содержание (G3)
3. Разделитель: Аналитика (G2)
4-8. Контентные слайды аналитики (A1-A4, B1-B4, C1-C5)
9. Разделитель: Стратегия (G2)
10-14. Контентные слайды стратегии (D1-D6, E1-E5)
15. Ключевые выводы (E2)
16. Рекомендации / Roadmap (E1, E3)
```

Итого: 16 слайдов. НЕ 40.

### Режим: полная презентация vs отдельный блок

**КРИТИЧНО.** Перед началом работы определи масштаб запроса:

| Сигнал | Режим | Сколько слайдов |
|--------|-------|-----------------|
| «Сделай презентацию», «АТС», «стратегия» + много разных данных | **Полная презентация** | 12–20 слайдументов (титул + содержание + разделители + контент) |
| Один конкретный блок данных: интервью, опрос, конкуренты, CJM | **Отдельный блок** | 1–5 контентных слайдов, БЕЗ титула/содержания/разделителей |
| Несколько блоков, но не полная дека | **Набор блоков** | 3–10 слайдов, минимум навигации |

**Правило определения режима:** если пользователь передаёт данные одного типа (например, только результаты интервью, или только анализ конкурентов) — это **отдельный блок**. Не раздувать до полной деки. Один блок данных = 1–5 слайдов максимум.

**Примеры:**
- «Вот результаты 12 интервью, сделай слайды» → блок, 2–4 слайда (сводка + ключевые цитаты + выводы)
- «Вот таблица конкурентов» → блок, 1–3 слайда (матрица + комментарий)
- «Сделай АТС для Берёзки, вот все данные» → полная презентация, 15–20 слайдов

### Режим: интерактивный материал для клиентской встречи

Этот режим включается по сигналам: `HTML для встречи`, `клиентский экран`, `Q&A`, `карта аргументов`, `decision memo`, `собери, чтобы пройти с клиентом`. Он нужен, когда на живой встрече участники должны не линейно смотреть деку, а быстро переходить между вопросами, доказательствами, вариантами решения и следующим действием.

`Интерактивный материал для клиентской встречи` остаётся режимом `pp-slidument`, а не отдельным скиллом и не параллельным маршрутом. До HTML обязателен существующий production Markdown: для него можно использовать компактную спецификацию встречи вместо полноразмерного deck-spec. Все материальные утверждения по-прежнему получают source + locator + caveat в claim ledger.

Сначала выбрать один из четырёх носителей:

| Носитель | Когда применять | Что должен обеспечить |
| --- | --- | --- |
| Q&A | у клиента есть конкретные спорные или повторяющиеся вопросы | вопрос, прямой ответ, подтверждение, граница уверенности |
| Карта аргументов | нужно защитить рекомендацию или развилку | тезис, основания, возражение, ответ, решение |
| Companion к дашборду | цифры уже живут в дашборде, но требуют объяснения | метрика, интерпретация, причина, действие, ссылка на источник |
| Интерактивная записка решения | на встрече нужно выбрать вариант и зафиксировать следующий ход | варианты, критерии, последствия, решение, владелец и следующий шаг |

Базовая структура одного HTML-материала:

1. Тезис и управленческий вопрос встречи.
2. Навигация по вопросам или развилкам.
3. Прямые ответы и подтверждения из именованных источников.
4. Что нужно решить сейчас.
5. Следующее действие, его владелец и evidence-gate, если решение пока нельзя принять.

Правила языка:

- писать от лица совместной рабочей команды: `мы`, `у нас`, `зафиксировано`; не говорить о клиенте в третьем лице;
- не подменять фактическое подтверждение словами `уже заложено` или `видно в данных`: рядом должен быть конкретный источник и локатор;
- не переносить в материал спор из чата, внутренние комментарии, реакции на правки или неподтверждённые обещания;
- источник, ограничение и статус гипотезы показывать рядом с сильным утверждением, а не прятать в общий методический блок.

Не создавать искусственную 16:9-деку, если задача решается самостоятельным HTML-companion. Для такого companion обязательны брендовый и evidence-контракт PP, `deliverable-clean-room`, проверка навигации, desktop/mobile рендер, отсутствие горизонтального overflow и проверка всех внутренних ссылок. Если HTML содержит полноценные 16:9-слайды или PP Pages shell, к нему применяются все deck-гейты этого скилла, включая slide grammar, SCA ledger, contact sheet и критиков.

Нельзя использовать этот режим для скрытого обхода production Markdown, claim ledger, PP Presentation Kit или клиентского QA.

**Каждый контентный слайд ОБЯЗАН содержать хотя бы один из:**

| Элемент | Когда использовать | Реализация |

## 1. МЕТОДОЛОГИЯ

### Core Principles

**SCA Structure** — каждый контентный слайд содержит завершённое рассуждение:
- Situation: релевантные факты, предпосылки и текущее состояние;
- Complication: почему это препятствует целям клиента, создаёт риск, разрыв или развилку;
- Answer: применимая модель, вывод, решение, гипотеза или следующий evidence gate.

ССА задаёт логику, но не навязывает три одинаковые колонки. Используй причинную схему, матрицу, дерево, flow, сравнение, декомпозицию или график, если они лучше раскрывают переход. Заголовок обязан выражать Answer. Обложка, разделитель, протокольный слайд и технический appendix могут иметь `SCA_not_applicable` с причиной.

**Action Titles** — заголовок = вывод, не описание темы:
- WRONG: «Анализ продаж», «Итоги исследования»
- RIGHT: «Объём продаж вырос на 15% за счёт трёх категорий»
- Тест: прочитать только заголовки подряд → связная история с выводами

**MECE** — взаимоисключающие, совокупно полные элементы. Нет пересечений, нет пропусков.

**Пирамида Минто** — главная мысль в заголовке, поддерживающие аргументы ниже, детали в нижних уровнях.

**Триангуляция** — минимум 2 источника из разных категорий на каждый слайд.

**Ценность, а не деятельность** — фокус на том, что клиент получит, а не на том, что мы будем делать. Измеримые результаты, инициативы роста.

### Библиотека типов слайдов (33 типа, 7 категорий)

- Полный каталог типов с паттернами верстки → `references/slide_types.md`
- Гайд: как давать вводные для каждого типа слайда → `references/usage_guide.md`

| Кат. | Название | Примеры типов |
|------|----------|---------------|
| **A** | Исследования и сбор данных | Сводка интервью, Результаты опроса, Тайный покупатель, NPS/Лояльность |

| **C** | Клиент и путь | CJM, Сегментация/Портрет, Unit-экономика, Воронка |
| **D** | Данные и аналитика | Декомпозиция, SWOT, ABC/BCG, Финпоказатели, Оргструктура, Бизнес-процессы |
| **E** | Стратегия и рекомендации | Позиционирование, Ассортимент, Ценообразование, Каналы, Продвижение, Roadmap, Скоринг, ROI |

```
Фаза проекта?
├─ Аналитический этап
│  ├─ Есть данные интервью? → A1 Сводка интервью
│  ├─ Есть данные опроса? → A2 Результаты опроса
│  ├─ Есть mystery shopping? → A3 Тайный покупатель
│  ├─ Нужен анализ конкурентов? → B1 Анализ конкурентов
│  ├─ Нужен размер рынка? → B2 Market Sizing
│  └─ Нужна декомпозиция? → D2 Декомпозиция
├─ Стратегия
│  ├─ Позиционирование? → D1
│  ├─ Ценообразование? → E3 (через Roadmap)
│  ├─ Каналы? → E4 (через Roadmap)
│  └─ План действий? → E1 Рекомендации

```

### Передовые практики консалтинговых презентаций

**Контент:**
- Значение вместо деятельности: фокус на том, что клиент получит, а не на том, что мы будем делать
- Измеримые результаты: конкретные, но обобщённые цифры и показатели успеха
- Инициативы роста: формулировка через возможности роста, не гарантии
- Стратегическое мышление: демонстрация глубокого понимания бизнеса клиента

**Визуализация:**
- Последовательное повествование: логическое развитие идей от слайда к слайду
- Контрастные акценты: красные (#FF5850) линии под заголовками для выделения ключевых разделов
- Пространство вокруг элементов: достаточно воздуха для лёгкости восприятия
- Визуальное кодирование: красный = высокий приоритет, чёрный = основное содержание, #F9F9F9 = фон вспомогательных блоков, #D5D7DA = границы

**Кейс-стади и референсы:**
- Карточная структура: 3 колонки с чётким визуальным разделением
- Структурированность: заголовок, подзаголовок с акцентной линией, ключевые работы, результаты
- Нумерация результатов: 01, 02 на чёрном фоне
- Акцент на бизнес-результаты: измеримые показатели успеха

### Графические стандарты
- Тонкие рамки таблиц (0.3-0.75pt), цвет #D5D7DA
- **НИКАКИХ теней, градиентов, свечений** — только плоские элементы
- Шевроны (►) в CORAL между аналитическими секциями
- Акцентная полоска CORAL на левом краю ключевых ячеек
- Harvey Balls для индикаторов зрелости/полноты

## 4. TECHNICAL: python-pptx (только для Claude Code)

> Этот раздел используется только при генерации PPTX через python-pptx в Claude Code.
> Manus и другие HTML-генераторы могут пропустить этот раздел.

### Slide Format
- 13.333" × 7.5" (widescreen)
- Margins: 0.45-0.5" all sides
- Title: 18-24pt bold, left-aligned at top
- Sources: 10pt GRAY_MED at bottom

### Two-Layer Adaptive Sizing

1. **Formula** — `calc_adaptive_size()` computes approximate font size
2. **Safety net** — `normAutofit` on every content shape (PowerPoint shrinks-to-fit)

### Calibrated Constants

| Parameter | Value | Rationale |
|-----------|-------|-----------|
| `ARIAL_CHAR_WIDTH` | **0.58** | Cyrillic average. Ш/Щ/Ж/Ю are 0.66-0.73 |
| `TARGET_FILL` | **0.78** | 22% safety margin for word-wrap waste |
| `LINE_HEIGHT_RATIO` | **1.15** | For formula only (NOT for setting line spacing!) |
| `bullet_extra` | **3.0 pt/item** | space_before + space_after + engine overhead |
| `MIN_PT` | **10.0** | Hard minimum readability floor |
| `MAX_PT` | **14.0** | Hard max for body text |

### Adaptive Sizing Formula

```python
def calc_adaptive_size(cw, ch, total_chars, margin_l, margin_r, margin_t, margin_b,
                       n_items=0, target_fill=0.78, min_pt=10.0, max_pt=14.0):
    aw = (cw - margin_l - margin_r) * 72
    ah = (ch - margin_t - margin_b) * 72
    bullet_extra = max(0, (n_items - 1)) * 3.0
    th = ah * target_fill - bullet_extra
    denom = total_chars * 0.58 * 1.15
    s = sqrt(th * aw / denom)
    s = clamp(s, min_pt, max_pt)
    s = round(s * 4) / 4
    return s
```

### Shadow Removal (mandatory)

```python
def remove_all_shadows(slide):
    for shape in slide.shapes:
        sp = shape._element
        for effectLst in sp.findall('.//' + qn('a:effectLst')):
            effectLst.getparent().remove(effectLst)
        spPr = sp.find(qn('p:spPr'))
        if spPr is None:
            spPr = sp.find('.//' + qn('a:spPr'))
        if spPr is not None:
            for eff in spPr.findall(qn('a:effectLst')):
                spPr.remove(eff)
            etree.SubElement(spPr, qn('a:effectLst'))
    for tbl in slide.shapes:
        if tbl.has_table:
            for effectLst in tbl._element.findall('.//' + qn('a:effectLst')):
                effectLst.getparent().remove(effectLst)
```

## 5. COMMON MISTAKES

For process, operating-model and organizational tables, the minimum useful dimensions are: `stage/process | handoff/result | owner | transfer or acceptance criterion | artifact | measurement/rhythm`. A row containing only a noun label such as “quality gates” or “changes and deadlines” is semantic underfill, not a finished exhibit.

## Eval hooks

When this skill changes, `skill-eval-harness` must test at least:

- an unsupported accent number or `X -> Y` arrow fails even when it is visually polished;
- an action title without a number passes when it states a specific evidence-backed conclusion;
- a slide with a large blank region and one generic sentence fails semantic-fill even if there is no overflow;
- a process table made of noun labels fails until it names owners, handoff results, artifacts, criteria and measurement;
- `Дизайн` is expanded to `Дизайн структуры` when structure is the actual object, and generic `контур` is expanded into the operating system or process it denotes;
- a user annotation invalidates prior receipts and triggers production-MD correction, whole-deck terminology sweep, rerender, contact-sheet review and target-PDF-renderer verification;
- a parent deck-run records actual, version-bound subskill receipts; proposed calls, missing critic reports, stale renders, and visually masked stale PDF text cannot pass the nested-skill or client-release gate;
- a comment scoped to subsequent slides of one type sweeps that exact population, while an explicit one-slide scope does not trigger a deck-wide rewrite; every edit keeps unchanged pages within the accepted regression boundary;
- a cover with viewer-dependent tint fails until the final PDF page is verified as viewer-safe DeviceRGB without unexpected ICC/SMask/transparency.
- a client-meeting HTML companion fails if it has no explicit meeting question, mixes answers with unsupported promises, or cannot navigate from a question to its named confirmation;
- a client-meeting HTML companion is not incorrectly forced into a 16:9 deck when its interactive reading scenario requires a non-linear page, but a deck-shaped companion still receives the full PP Pages and slide-level gate.
- each `subskill_run_trace` row is tied to the same parent run and deck revision; a named-but-not-invoked skill, stale critic report, or visually masked stale PDF text cannot pass release;
- a user comment scoped to subsequent slides of one type changes only that population; the trace lists checked locators and unchanged pages remain within the accepted regression boundary.

### Gamma: параметры фирменных иллюстраций

После команды штатному редактору создать диаграмму проверять сам слайд: успешный ответ может оставить пустой блок изображения. Если схема не отрисована, заменить его нативной редактируемой таблицей или встроенной схемой и проверить повторно; пустой блок не считать готовой визуализацией.
