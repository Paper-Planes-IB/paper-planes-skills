# /cordos

## Назначение

Показать Илье кандидатов в задачи для активного проектного маршрута задач.

`/cordos` не выполняет задачи и не пишет их автоматически в трекеры, Vault, Notion или внешние каналы. Это triage-режим: найти, что уже прозвучало как обязательство, next step, блокер, ручная задача, задача после созвона или долг когнитивного роутера, но ещё не заведено как нормальная задача.

Текущий writeback-режим: primary task route теперь `YouGile` или `ClickUp`, если конкретный контур / проект уже имеет там живой рабочий маршрут или Илья прямо просит этот маршрут. Автоматически пушить task_delta из `/cordos`, Soroka, Daily, heartbeat, `/summary` или `/tunnel` в YouGile / ClickUp нельзя: сначала показать кандидата или сохранить только локальный trace, если есть существующая посадка и акцепт на разнос. Старые контуры Task OS / Airtable / Codex Project Task Inbox / chat_manual / SQLite считать legacy/historical только для внутренней проверки дублей; не перечислять их в пользовательском ответе как отключённые маршруты и не выводить в `sync_status`, если Илья специально не спрашивает про старый контур.

## Когда использовать

- `/cordos`
- `покажи кандидатов в Cord OS`
- `что добавить в активный трекер`
- `зарегистрируй задачи в таблице задач`
- `какие задачи отсюда завести`
- `найди задачи для трекера`
- после длинного чата, созвона, project-progress-check, `/summary` или `/tunnel`, если появились действия

## Источники

Читать только нужный минимум:

- текущий чат и последние явные поручения пользователя;
- `Vault/Daily Notes/<год>/<ДД-ММ-ГГГГ>.md`;
- `Vault/60-отчёты/входящие/<ДД-ММ-ГГГГ>.md`, если есть свежий отчёт;
- проектные `Трекер-задач.md` и `_журнал-проекта/<ДД-ММ-ГГГГ>.md` по затронутым проектам;
- текущую механику активного трекера, если задача должна быть зарегистрирована как новая постановка;
- старые task-следы читать только при необходимости проверить исторический дубль; не использовать как рабочий контур и не выносить legacy-системы в пользовательский ответ без запроса.

## Штабной project-wide preflight

Если текущий чат по `Карта-чатов.md`, реестру чатов, карте коммуникаций или субпаспорту связан с контуром типа `штаб проекта`, `/cordos` всегда работает по всему проекту, а не только по текущему физическому чату.

Перед поиском кандидатов нужно:

- найти `Карта-чатов.md` / реестр чатов ближайшего проектного контура;
- определить штабной чат и связанные чаты / треки / субпаспорта проекта;
- прочитать проектный `Трекер-задач.md`, ближайшие проектные журналы и релевантные субпаспорта;
- проверять дубли по всему проектному контуру, а не только по текущему чату.

В ответе preflight показывать кратко: `штаб проекта -> project-wide scope -> какие чаты / треки / трекеры учтены`. Если реестр чатов не найден, явно написать, что проектный штабный scope не подтверждён, и работать по текущему чату / ближайшему проектному контексту.

## Что считать кандидатом

Кандидат появляется, если есть хотя бы один сильный сигнал:

- пользователь сказал `надо`, `сделай`, `добавь`, `проверь`, `подними`, `закрой`, `действуй`, `забрать`, `создать`, `обновить`;
- есть `next step`, `blocker`, `ждёт решения`, `нужно акцептовать`, `после созвона`;
- проект имеет открытый `description-gap`, `source-gap`, `management-gap`, `chat gate`, `BPM-scope`, `review`, `handoff`;
- задача нужна для активного трекера проекта, Daily Note, карты чатов, BPM/BPP, weekly-doc, SI/ARCH, КП или контентного слота;
- действие повторяется в нескольких местах, но не видно нормальной задачи.

Не считать кандидатом:

- свободную мысль без действия;
- знание, гипотезу, SI, source или Storyline-Storyboard delta без явного владельца, действия, срока/события и ожидаемого выхода;
- правило для `/meditate`;
- содержательную находку для `/summary`;
- маршрутизацию знания для `/tunnel`;
- уже закрытую задачу с evidence;
- задачу, которую нельзя сформулировать как `кто / что / к какой дате / зачем`.

## Task vs knowledge gate

Перед показом кандидата, выросшего из research, BPM/SI, Storyline-Storyboard, `/tunnel`, `/summary` или внешнего return packet, классифицировать сигнал:

- `task` — есть владелец/контур, действие, срок или событие, ожидаемый выход и зачем это двигает проект;
- `knowledge_update` — нужно обновить Vault / Storyline-Storyboard / методологию, но нет самостоятельного действия;
- `both` — есть и durable knowledge update, и отдельное действие;
- `neither` — сигнал полезен для рассуждения, но не требует записи в задачу.

В активный трекер предлагать только `task` или task-часть `both`. Для `knowledge_update` показывать ближайший writeback target или no-op, но не превращать знание в задачу ради фиксации. Если активный маршрут не определён, писать `route_pending` / `пока только помнить`, а не перечислять старые запрещённые контуры.

## Проверка дублей

Перед показом кандидата быстро проверить:

- есть ли задача в проектном `Трекер-задач.md`;
- есть ли она в месячном / субтрековом трекере, если проект New Delivery;
- есть ли она уже в активном проектном трекере;
- есть ли старые task-следы только как historical duplicate-check, если это действительно нужно для антидубля;
- не является ли она регулярной задачей, которую уже порождает шаблон.

Если дубликат вероятен, показывать строку как `дубль?` с указанием найденного источника, а не как новую задачу.

## Формат ответа

Начинать с BLUF:

```text
Нашёл N кандидатов: X можно заводить, Y требуют уточнения, Z похожи на дубли.
```

Дальше таблица:

| # | Проект / контур | Кандидат в задачу | Владелец | Срок | Зачем | Источник | Куда добавить | Статус |
|---|---|---|---|---|---|---|---|---|

Статусы:

- `заводить` — достаточно данных для регистрации в активном трекере после акцепта Ильи;
- `уточнить` — не хватает владельца, срока, проекта или результата;
- `дубль?` — похожая задача уже есть;
- `не заводить` — мысль полезная, но не задача.

После таблицы дать короткий блок:

```text
Рекомендую завести сейчас:
- ...

Нужно уточнить:
- ...
```

## Запись задач

По умолчанию `/cordos` только показывает кандидатов.

Если пользователь подтверждает конкретный список, основной маршрут:

1. Если у проекта / контура primary route уже определён как `YouGile` или `ClickUp`, готовить task_delta под этот маршрут, но не писать туда без отдельной прямой команды на запись / обновление.
2. Для явных Basecamp-команд зарегистрировать задачу в Basecamp по правилам Basecamp-пилота, если этот маршрут всё ещё явно задан пользователем для конкретного случая.
3. Для остальных контуров без активного трекера оставить proposal-only и локальный trace / `route_pending`.
4. Если нужно сохранить legacy-след, обновить существующий проектный `Трекер-задач.md` / месячный / субтрековый трекер только через patch и подтверждение.

Запись в Vault, Notion или внешние сообщения — только после явного акцепта Ильи. Прямая команда Ильи `создай / закрой / сними / перепиши задачу` считается акцептом на запись в активный трекер, если он определён. Перед записью всегда показать или зафиксировать, куда именно пойдёт task-delta: `YouGile`, `ClickUp`, явный project-specific live tracker или `route_pending / пока только помнить`.

## Минимальный стандарт задачи

Любая рекомендуемая задача должна быть приведена к формату:

- кто отвечает;
- что сделать;
- к какой дате или к какому событию;
- какой выход должен появиться;
- зачем это двигает проект / контур.

Если срок неизвестен, писать `ближайшее касание` или `после <событие>`, но явно отмечать это как слабое место.

## Writeback / Approval Gate

Этот skill считается рискованным, потому что может превратить разговор, отчёт или проектный сигнал в задачи и тем самым изменить операционный контур.

По умолчанию `/cordos` показывает только кандидатов. Создание задачи, правка активного трекера, обновление Daily Note, отправка задачи в Notion/внешний канал или изменение статуса допускаются только после явного акцепта Ильи на конкретный список задач. Перед записью показать: ID/название, владелец или контур, срок/событие, ожидаемый выход, зачем это нужно, и место записи. Если место записи не YouGile / ClickUp / явно заданный live tracker, не подбирать суррогатный маршрут и не перечислять legacy-стек в ответе.
